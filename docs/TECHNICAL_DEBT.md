# Technical Debt

Findings only — nothing in this document has been fixed as part of this documentation pass, by design (see project instructions: documentation should not change application behavior).

## Critical

### TD-001 — No server-side authentication on any `/api/admin/*` route
**Problem**: Zero auth/session/token check in any of the 6 admin route handlers. **Current implementation**: unconditional execution of the requested action. **Impact**: full read/write access to the entire admin surface for any network caller. **Risk**: Critical. **Recommended solution**: add a real session mechanism (e.g. Supabase Auth + a server-side session check in each route, or middleware) before any non-local deployment. **Complexity**: Medium (needs an auth provider decision + route-by-route guard + RLS policy rework, see TD-003). **Affected areas**: all [`app/api/admin/*`](../app/api/admin), `AUTHENTICATION.md`, `SECURITY.md`.

### TD-002 — Admin login is a client-side-only, hardcoded, default-open gate
**Problem**: Credentials shipped in client source; `isAuthenticated` defaults to `true`. **Impact**: no real identity assertion even for the UI, independent of TD-001. **Risk**: Critical. **Recommended solution**: replace with a real auth flow (server-verified session/token), remove hardcoded credentials from source entirely. **Complexity**: Medium. **Affected areas**: [`components/admin/AdminLoginPage.tsx:27`](../components/admin/AdminLoginPage.tsx#L27), [`app/admin/page.tsx:56`](../app/admin/page.tsx#L56).

### TD-003 — Fully public RLS write policies on all Supabase tables and the storage bucket
**Problem**: `using (true)` / `with check (true)` policies with no ownership/role scoping. **Impact**: the public anon key can read/write `artisans`, `products`, `product_feedback`, and upload to `product-images` directly, bypassing the Next.js server and any auth added by TD-001/TD-002. **Risk**: Critical for any deployment with real user data. **Recommended solution**: introduce auth-scoped RLS policies once real authentication exists; until then, do not treat this schema as safe for a public deployment with real user data. **Complexity**: Medium, but blocked on an auth design decision. **Affected areas**: [`supabase/schema.sql:37`](../supabase/schema.sql#L37), `SECURITY.md`, `DATABASE.md`.

## High

### TD-004 — In-process memory state does not survive multiple server instances or restarts
**Problem**: [`lib/supabase/products.ts:14`](../lib/supabase/products.ts#L14), [`lib/supabase/feedback.ts:118`](../lib/supabase/feedback.ts#L118), [`lib/supabase/admin.ts:213`](../lib/supabase/admin.ts#L213) each keep a module-level `Map`/variable as a fallback cache; this is assumed to be the *only* store for large parts of the admin domain (customers, activity log, settings, artisan directory status). **Impact**: any multi-instance or serverless deployment will show inconsistent/lost data across instances/restarts; even single-instance deployments lose all of this on restart. **Risk**: High for any real deployment; low for local single-process demo use, which is the currently supported use case. **Recommended solution**: move this state into Supabase tables (would require new tables for customers/activity/settings — none exist today) or another shared store. **Complexity**: Medium-High (schema design + rewire of `lib/supabase/admin.ts`). **Affected areas**: `DEPLOYMENT.md`, `DATABASE.md`.

### TD-005 — Review moderation status, customer leads, activity log, and platform settings never reach Postgres
**Problem**: No corresponding tables exist in [`supabase/schema.sql`](../supabase/schema.sql); these features are `localStorage`-only. **Impact**: not real multi-admin/multi-device features despite appearing as such in the UI; data loss on browser storage clear. **Risk**: High (misleading admin UX — an admin could reasonably assume these actions are durable). **Recommended solution**: add tables (`customer_leads`, `activity_log`, `platform_settings`) and a `status` column to `product_feedback`, then rewire `lib/supabase/admin.ts`. **Complexity**: Medium. **Affected areas**: `DATABASE.md`, `admin-cms.md`.

### TD-006 — No automated test suite
**Problem**: zero test files, no CI. **Impact**: every change described above (and any future change) is verified only by manual exercise. **Risk**: High, compounding over time as the codebase grows. **Recommended solution**: start with unit tests for the pure functions ([`getMockGeneration`](../lib/ai/visart.ts#L173), [`getMockAuthenticityAudit`](../lib/ai/authenticity.ts#L143), Zod schemas) and integration tests for the route handlers; see [TESTING.md](TESTING.md) for a starting checklist. **Complexity**: Medium to start, ongoing investment.

### TD-007 — No rate limiting on paid-API-backed or public-write endpoints
**Problem**: `/api/generate`, `/api/verify-authenticity` (both call paid Gemini API) and `/api/feedback` (public write) have no throttling. **Impact**: unbounded cost exposure and spam exposure. **Risk**: High once internet-facing. **Recommended solution**: add per-IP/per-session rate limiting (e.g. via middleware or an edge-level solution). **Complexity**: Low-Medium.

## Medium

### TD-008 — Duplicated, hand-synchronized contracts across files
**Problem**: the Gemini candidate-model list exists independently in [`lib/ai/visart.ts:139`](../lib/ai/visart.ts#L139) and [`lib/ai/authenticity.ts:21`](../lib/ai/authenticity.ts#L21); the `VisartGeneration` shape exists independently as a Zod schema ([`lib/validation/visart.ts`](../lib/validation/visart.ts)), a Gemini response schema ([`lib/ai/visart.ts:4`](../lib/ai/visart.ts#L4)), and a hand-written TS type ([`types/visart.ts`](../types/visart.ts)); [`types/database.ts`](../types/database.ts) is a hand-written mirror of `supabase/schema.sql`. **Impact**: easy to silently desync when changing one without the others (documented per-file in [FEATURE_DEPENDENCIES.md](FEATURE_DEPENDENCIES.md)). **Risk**: Medium, self-inflicted bugs over time. **Recommended solution**: consider generating the Gemini schema from the Zod schema (or vice versa), and generating `types/database.ts` via the Supabase CLI from the live schema. **Complexity**: Medium.

### TD-009 — Admin dashboard/analytics/performance metrics are partly hardcoded or randomized, not measured
**Problem**: [`lib/supabase/admin.ts`](../lib/supabase/admin.ts) — [`growthRates`](../lib/supabase/admin.ts#L318), [`generationLatency`/`chatResponseLatency`/`conversionRate`/`cacheHitRate`/`popularCraftCategories`](../lib/supabase/admin.ts#L630), per-product [`totalInquiries`](../lib/supabase/admin.ts#L349), [`geminiAi`/`audioEngine` status fields](../lib/supabase/admin.ts#L608), and simulated `uptimeSeconds` are static or `Math.random()`-derived, not measured from real telemetry, alongside genuinely-computed fields (total products, total reviews) in the same response objects with no naming convention distinguishing the two. **Impact**: misleading if presented to a real stakeholder as live metrics. **Risk**: Medium (reputational/decision-making risk if trusted, not a technical failure risk). **Recommended solution**: either wire these to real telemetry (would require adding an events/analytics pipeline, which does not exist) or clearly label simulated fields in the UI. **Complexity**: High to make real, Low to relabel honestly in the interim.

### TD-010 — "Verified Buyer" and review authenticity are not independently verified
**Problem**: `isVerifiedBuyer` is hardcoded `true`; no purchase/order record exists to check against. **Impact**: undermines the credibility premise of the anti-counterfeit feedback system. **Risk**: Medium. **Recommended solution**: introduce an order/purchase concept if this becomes a real commerce platform, or relabel the badge honestly until then. **Complexity**: High (requires a checkout/order system that does not exist at all today).

### TD-011 — `next.config.mjs` allows Next Image Optimization to fetch any remote host
See [SECURITY.md](SECURITY.md) finding #8. **Recommended solution**: narrow `images.remotePatterns` to known hosts (Supabase Storage domain, Unsplash if seed images stay hosted there). **Complexity**: Low.

## Low

### TD-012 — Two separate, largely redundant demo-product constants
**Problem**: [`lib/data/seed.ts`](../lib/data/seed.ts) (`SEED_PRODUCTS`, actively used throughout) and [`lib/demo/demoProduct.ts`](../lib/demo/demoProduct.ts) (`demoProduct`, a single static object, used only by [`components/landing/TransformationSection.tsx`](../components/landing/TransformationSection.tsx)) overlap in purpose. **Impact**: unclear which is authoritative; risk of editing the wrong one. **Recommended solution**: confirm whether `demoProduct.ts` is still referenced anywhere meaningfully and consolidate or remove if dead. **Complexity**: Low (needs a usage-site check before removal).

### TD-013 — Unconditional debug logging in production code paths
**Problem**: several `console.log`/`console.warn` calls in [`lib/supabase/products.ts`](../lib/supabase/products.ts) and [`app/api/generate/route.ts`](../app/api/generate/route.ts) are not gated by `NODE_ENV === "development"` (unlike most of [`lib/ai/visart.ts`](../lib/ai/visart.ts)'s logging, which is gated). **Impact**: unnecessary log volume in production; minor. **Recommended solution**: gate consistently. **Complexity**: Low.

### TD-014 — Dead product-page components and inaccurate/disconnected copy
**Problem**: [`components/product/ArtisanStory.tsx`](../components/product/ArtisanStory.tsx), [`ProductDetails.tsx`](../components/product/ProductDetails.tsx), and [`ProductHero.tsx`](../components/product/ProductHero.tsx) are not imported anywhere — [`ProductView.tsx`](../components/product/ProductView.tsx) implements the equivalent UI inline instead, so these three files are unreachable dead code. Separately, [`AuthenticityInspector.tsx`](../components/product/AuthenticityInspector.tsx) contains UI copy claiming the audit is "cryptographically grounded," which is inaccurate — it is a plain LLM text analysis with no cryptographic verification of any kind. The landing page's [`FairPricingWidget.tsx`](../components/landing/FairPricingWidget.tsx) and [`VoiceAccessibilitySection.tsx`](../components/landing/VoiceAccessibilitySection.tsx) also run their own independent, disconnected logic rather than reusing the real pricing/voice pipelines used elsewhere in the app — they illustrate the feature, they don't exercise it. **Impact**: dead code adds maintenance confusion (a future edit to the "real" product page UI might mistakenly be made in one of the unused files instead); the inaccurate copy could mislead a buyer about how the authenticity system actually works. **Risk**: Low (no functional or security impact, but a correctness/trust issue in user-facing copy). **Recommended solution**: delete the three dead components (or wire them in if they were meant to be used) and correct the "cryptographically grounded" claim to reflect that it's AI-based analysis. **Complexity**: Low.
