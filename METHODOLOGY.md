# Methodology

How Visart produces the listing, price range, readiness scores, authenticity report and review risk flags it shows, and which of those come from the Gemini model, from fixed rules or from placeholder data. Everything here is implemented in `lib/ai/`, `lib/supabase/` and `lib/frontend/`. The `docs/features/` folder has per-feature detail, and this file collects the scoring rules in one place.

The short version: **Visart does not measure authenticity, market price or readiness.** Each is text and numbers written by a language model from what the artisan typed, or, in demo mode, fixed templates. They are drafting aids, not verification.

## 1. Demo mode and real mode

A single flag decides how the app behaves:

$$\text{demo mode} = \bigl(\texttt{NEXT\_PUBLIC\_VISART\_DEMO\_MODE} \ne \texttt{"false"}\bigr)$$

It is **on unless the variable is exactly `false`**, including when the variable is missing.

| | Demo mode (default) | Real mode |
| :--- | :--- | :--- |
| Listing generation | The browser builds a template listing itself and never calls the server | The browser calls `/api/generate`, which calls Gemini |
| Gemini failure | Returns the template listing silently | Returns an error |
| Authenticity report | Template report when no `GEMINI_API_KEY` is set. With a key, the server uses Gemini | Gemini, with template fallback |
| Data | Memory, browser storage and seed products, with Supabase if configured | Same, see §7 |

So unless the flag is set to `false` and a key is configured, listing generation is a template filled with the artisan's words, and the authenticity report is a template whenever no key is set.

## 2. Listing generation

In real mode one prompt goes to Gemini with the artisan's inputs (name, material, cost, time, location, special details) and an optional photo (resized to at most 1,200 px on its longest side and sent as JPEG at quality 0.85). The model is told to rely only on the provided facts, to avoid invented heritage, awards or certifications, and to avoid a list of clichés. The reply is constrained by a JSON schema, then validated with Zod before it is used.

**Model fallback.** The server tries the model in `GEMINI_MODEL`, then five built-in model names in order. Each candidate gets 2 attempts, with a wait of 1.2 s times the attempt number after a transient error. An error is "transient" if its text contains 503, 429, 404, "not found", "unavailable", "timeout" and similar words, so an unknown model name is retried once and then skipped.

The facts-only rule is an instruction to the model. Nothing checks the output against the inputs, so invented details are still possible.

## 3. Price range

**Real mode.** The pricing numbers are whatever Gemini returns for the instruction "fair-trade pricing guidance in INR based on raw material cost and labor time". There is no formula in the code and no market data, and the code does not check that the minimum, recommended and maximum values are in order or relate to the cost. Earlier README text described a formula with a "fair-trade multiplier"; it does not exist.

**Demo mode.** With production cost $c$ in rupees:

$$\min = \mathrm{round}(1.8\,c),\qquad \text{recommended} = \mathrm{round}(2.2\,c),\qquad \max = \mathrm{round}(2.8\,c)$$

The three "rationale" lines are fixed sentences that mention the cost, the time and the region, and do not come from analysis. A separate illustrative calculator on the landing page uses a third, unrelated formula and is not connected to either.

## 4. Digital readiness scores

The readiness panel (overall, photography, description, discoverability, pricing presentation, marketing, and three actions) is generated by Gemini in real mode, as scores from 0 to 100 that are not tied to any rubric in the code.

In demo mode they are **constants**: overall 84, description 90, discoverability 82, pricing 88, marketing 85, and photography 85 when a photo is given or 55 when not. The overall value is not computed from the others.

## 5. Authenticity report

The report has an overall score, a verdict (`VERIFIED_AUTHENTIC`, `LIKELY_AUTHENTIC`, `SUSPICIOUS` or `HIGH_RISK_FAKE`), three sub-scores (material, technique, pricing) and "how to spot a fake" tips.

**In real mode** it is a single Gemini prompt containing the listing text the artisan's inputs produced, the stated cost, the listed price and a sample of buyer comments. **The product photo is not part of the prompt**, and no physical or image check is made. The model is asked to judge, for example, whether the claimed material is realistic for the cost and region. This is a language-model opinion about a description.

Three implementation details change how the result reads:

- If the call fails or returns nothing, the code returns the template report **even outside demo mode**.
- Missing or zero fields from the model are replaced with 95, so a model score of 0 reads as 95: `parsed.overallScore || 95`, and `VERIFIED_AUTHENTIC` for a missing verdict.
- The template report is optimistic by design: with $f$ buyer fake-flags,

$$\text{overall} = \begin{cases} 96 & f = 0 \\ \max(60,\ 94 - 15f) & f > 0 \end{cases}\qquad \text{verdict} = \begin{cases} \texttt{SUSPICIOUS} & f \ge 2 \\ \texttt{VERIFIED\_AUTHENTIC} & \text{otherwise} \end{cases}$$

with the sub-scores fixed at 98, 95 and 94.

**Community trust score** (both modes) is the share of buyer reviews rated "genuine handcrafted" or "likely genuine", as a rounded percentage. With no reviews it shows **96**, not "no data".

## 6. Buyer feedback and fake flags

When a buyer submits a review, the text goes through a risk classifier.

- **Keyword check.** The comment and the stated reason are searched for 11 words and phrases such as "fake", "plastic", "synthetic", "machine made", "powerloom" and "counterfeit".
- **With Gemini.** The model returns a risk score from 0 to 100, a short assessment and flagged keywords. If it omits the score, 75 is used when a keyword matched and 10 otherwise.
- **Without a key.** If the buyer rated the product "suspicious quality" or "confirmed fake replica", the risk is 85 with a keyword match and 65 without. Otherwise it is 5.
- **Fake flag.** A review is flagged as fake when the buyer chose one of those two ratings, or the risk is above 60.

Every review is marked "Verified Buyer", because the app has no orders to verify. Anyone can submit a review, and the comment text is placed inside the model prompt without being checked, so it can be used to flag a rival's product or to try to steer the classifier.

## 7. Storage

Writes always go to an in-process map and the browser's local storage first, and then to Supabase if it is configured and the write works. Reads check the map, then local storage, then seed data, and only then Supabase. The effect is that a product can look different in different browsers, and a dashboard can show data that is not in the database. The reasons are in `docs/adr/001-demo-mode-dual-persistence.md`.

## 8. Limitations

- **Nothing is verified.** The authenticity report, price range and readiness scores are not backed by data, images or experts.
- **Demo mode is the default**, so many "AI" outputs are templates.
- **Admin metrics are partly invented.** Growth rates, latency and conversion figures in the admin dashboard are static or random values (`docs/TECHNICAL_DEBT.md`, TD-009).
- **No access control** on the admin routes or on writes to the database tables (see the README's Security section).
- **Translations** into Hindi and Kannada come from the same model call and have not been reviewed by speakers of those languages.
- **No automated tests** exist for any of the logic above.
